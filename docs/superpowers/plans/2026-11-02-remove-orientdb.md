# Remove OrientDB and Unused Dependencies Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Remove the OrientDB instance store, its modules and libraries, move TinkerPop 2 to the official 2.6.0 release, and sweep all version catalogs and module dependency declarations for unused entries.

**Architecture:** Pure removal and build-configuration work in the Gradle multi-module build. Modules are discovered automatically by `settings.gradle` (every directory with a `build.gradle`) and added to the `bom` automatically; `bom-deps` exports every `libs` catalog alias. No new production code.

**Tech Stack:** Gradle (version catalogs `gradle/libs.versions.toml`, `gradle/test-libs.versions.toml`, `gradle/resources.versions.toml`), Java 17 (via mise), JUnit 4, Groovy.

**Spec:** `docs/superpowers/specs/2026-11-02-remove-orientdb-design.md`

## Global Constraints

- Conventional Commits; footer `ING-4137` on every commit; no `Co-authored-by`.
- The OrientDB removal commit is a breaking change listing the removed modules; do not edit `CHANGELOG.md` (generated by semantic-release).
- `StoreInstancesJob.TASK_TYPE` keeps the value `eu.esdihumboldt.hale.instance.orient.store`.
- `InstanceStoreExtension` keeps its priority/fallback mechanism unchanged.
- TinkerPop 2 version: `2.6.0`; no move to TinkerPop 3.
- Do not touch `common/plugins/eu.esdihumboldt.hale.common.align.tgraph*`, `ext/xslt/*`, or historic files under `docs/superpowers`.
- The BOM reflects only what hale-core uses: removing an unused `libs` entry is not a breaking change.
- Sweep removals only after the user approved the findings list.
- Work on branch `stempler/remove-orientdb`. Run Gradle via `mise x -- ./gradlew ...` if Java is not on the path.

## Review Focus

1. Users or scripts that still pass `-Dhale.instance.store=orient` → a warning is logged and the SQLite store is used (pinned in Task 1, `testRequestedUnknown` keeps `"orient"` as the requested id).
2. TinkerPop 2.6.0 brings different transitive libraries (e.g. Jackson, Jettison, commons-configuration) than the custom build → GML partitioned writing keeps working and no unexpected new libraries land on the runtime classpath (Task 2, runtime classpath diff plus `io.gml` tests).
3. A dependency that is only used at runtime (`plugin.xml` extension classes, `META-INF/services`, class names in strings, Groovy scripts, JDBC drivers, logging backends, offline resources looked up by URL) is judged unused → the CLI transformation still works (Task 3 runtime-use checks; Task 4 full build including `app.transform` CLI tests).
4. Modules that got libraries transitively via `common.feature.orient` / `instance.orient` (`api` deps `eclipse-collections-api`, `orientdb-core`, `orient-commons`) → still compile and pass (Task 1 full build).
5. A removed module still referenced somewhere (feature `build.gradle`, test runtime dependency) → `git grep` for the module names returns nothing outside historic docs (Task 1 step).

### Task 3: Sweep — find and report unused dependencies

No commits. Output: a findings report for the user, saved to `<scratchpad>/dependency-sweep.md` and summarized in chat.

**Interfaces:**
- Consumes: state after Tasks 1 and 2.
- Produces: the findings list (each entry: catalog alias or `module → dependency`, evidence, group "clearly unused" / "unsure, needs a decision").

- [ ] **Step 1: Unreferenced catalog entries.** For every alias in all three catalogs (libraries, bundles, plugins, versions), check whether any `build.gradle` (including `buildSrc`, `bom`, `bom-deps`, `settings.gradle`) references it, considering the accessor form (`foo-bar-baz` → `libs.foo.bar.baz`), bundle membership, `version.ref` use, and programmatic access (`findLibrary`, `findVersion`, `libs.versions.x.get()`). Note `bom-deps` exports all `libs` aliases — that alone does not count as use.

- [ ] **Step 2: Unused declared module dependencies.** For every module, compare declared dependencies (project and library) with what its main and test sources (Java and Groovy) import or reference. Tool choice is free (e.g. a local, uncommitted Gradle dependency analysis plugin, or grep over imports against the packages of each dependency jar). Known finding: `io/plugins/eu.esdihumboldt.hale.io.wfs/build.gradle` declares `common.instance.graph` without using it.

- [ ] **Step 3: Runtime-use check for every candidate.** Before listing a candidate as "clearly unused", search for: classes in `plugin.xml` / `resources/main/plugin.xml`, `META-INF/services`, class or package names in strings, Groovy scripts and test resources, JDBC drivers and logging backends, offline resources (resources catalog) looked up by URL at runtime, and entries that exist to pin a transitive version (e.g. for a security fix). Anything with such a hint goes to "unsure" with the hint as evidence.

- [ ] **Step 4: Report** to the user: both groups with evidence, and stop until the user says which entries to remove.
